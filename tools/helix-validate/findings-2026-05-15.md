# Empirical Findings — Helix engine state (post this-session fixes)

> Goal of this run: verify what the LEA / SETcc / BT / Win64-entry-point /
> AddressSpace / segment-intrinsic fixes from the May 14 session actually
> changed *in practice*, by re-decompiling the `malware.ko` (HTB
> `rev_kernel_monarch`) corpus end-to-end with the current engine via
> `helix_tool.exe` (standalone, no extension cache) and comparing
> side-by-side against the existing `hexcore-reports/02-disasm/` outputs.
>
> **Result: honest, mixed, and instructive.** Three real wins on `malware.ko`,
> one new bug discovered in the lifter, and most of `malware.ko`'s
> Helix-side issues (G-001, G-002, G-015) are unaffected by this session's
> fixes — those fixes targeted PE/Win64 lift paths that ELF/SysV does not
> exercise.

## 1. Setup

Job: `lift-only-malware.hexcore_job.json` — produces seven per-function `.ll`
files under `hexcore-reports/02b-lift-only/` using the existing
`hexcore.disasm.liftToIR` (no Helix decompile step). Then `helix_tool.exe`
is run against each `.ll`, output to `hexcore-reports/02c-helix-tool/`.

Comparison baseline: the existing `hexcore-reports/02-disasm/3X-*.helix.c`
outputs that were produced earlier by the full VSCode pipeline (extension +
DWARF feeder + Pathfinder).

**Confound to keep in mind:** the OLD outputs came through the extension,
which provides the DWARF feeder and the symbol-rename pipeline.
`helix_tool.exe` standalone does *not* have either. So a NEW output can look
worse purely because field/parameter names are placeholders (`field_0xN`,
`vN`) where the OLD output had real DWARF names. We separate the
*engine-attributable* deltas from this confound below.

this function has no LEA write-back to a non-RCX register, no SETcc, no
bit-test, no segment-relative access, and is not a PE entry. The fixes are
PE-correct; this function is SysV/ELF.

## 3. New bug discovered: lifter emits conflicting `declare` + `define`

While running `fh_install_hook`, helix_tool parse-rejected the `.ll` with:

```
helix: <helix-input>:1152:13: error: invalid redefinition of function 'fh_install_hook'
declare ptr @fh_install_hook(...)
            ^
```

Root cause (verified in the `.ll`): the lifter emits both
`define ptr @fh_install_hook(ptr noalias %state, …)` at line 194 **and**
`declare ptr @fh_install_hook(...)` at line 1152. LLVM IR forbids a symbol
having both a definition and a forward declaration in the same module.

Cause: `fh_install_hook` makes a self-referential call (line 538:
`ptrtoint (ptr @fh_install_hook to i64)`). The lifter's symbol-collection
pass adds it to the external-symbol declarations block as if it were an
imported function. When the same symbol is *also* the one being lifted in
this `.ll`, the two emissions collide.

This bug is in **hexcore-remill** (the lifter), not Helix. Workaround used
for this study: strip `declare ptr @<X>(...)` lines whose `<X>` already has a
`define ptr @<X>(…)` earlier in the same `.ll`. The patched `.ll` parses and
decompiles cleanly. The lifter fix is to do this dedup at emit time.

This bug is not in the GAPS doc — it is new, and it is the *real* root cause
of `fh_install_hook`'s "silent failure" in the original VSCode run, because
the extension swallowed the parse error as "Expected output file was not
created" (G-010).

## 4. What this session's fixes actually changed

Putting the engine-only deltas together:

| Fix | What it targets | Observed effect on malware.ko |
|---|---|---|
| LEA write-back to any register | SysV/PE functions using LEA into non-RCX | No visible effect on this corpus (functions either don't use LEA, or use it only into RCX). |
| SETcc proper flag→bool | Any function using SETcc | No SETcc instructions in `init_module`/`hook_*` (verified by absence of the old `-6510615558205997056` placeholder). |
| BT/BTS/BTR/BTC `1 << (off & 63)` mask | Bit-test idioms | No bit-test patterns in this corpus. |
| Win64 entry-point detection | PE `start`/`hc_entry` | N/A — malware.ko is ELF, no PE entry. |
| AddressSpace structural recovery | `gs:`/`fs:` segment access | N/A — Linux kernel code does not use segment-relative addressing the way Win64 PEB access does. |
| `__readgsqword(N)` / `__readfsqword(N)` emission | Same as above | N/A — same. |
| Switch table case_values + RetOp default | Any function with a sparse switch table | Cannot test from helix_tool standalone — needs the DataSectionProvider wire-up that only the extension supplies. |

**So: this session's fixes are PE/Win64-targeted, and the malware.ko corpus
that motivated the v3.9.0 GAPS doc is ELF/SysV.** The fixes are real (we
saw them work on Echo Mirage entry_point: `entry_point(void)` instead of
phantom params, `__readgsqword(96)` emitted three times, confidence 100% on
clean output). They simply do not exercise on this corpus. The three
malware.ko wins (`fh_install_hook[s]`, `hook_ia32_write` name) appear to
come from *other* engine changes that landed between the OLD run and now
— pre-this-session work.

## 5. What still needs work for malware.ko

The four Helix gaps the docs system enumerated (G-001 helix-side, G-002,
G-010, G-015) are all visible in the byte-identical `init_module` output
above:

- **G-001** (wrong section selected) — present.
- **G-002** (placeholder/early-return) — present (`return sub_c();` line 1).
- **G-010** (silent failure) — partially resolved (visible parse error
  surface now, but the *underlying* lifter bug needs the §3 fix).
- **G-015** (inflated confidence) — present (91.0% on the byte-identical
  garbage output).

These are the real v0.9.1 work items if we want to close the malware.ko
case. They are *not* PE-specific.

## 6. What helix-validate tells us — interpreted honestly

Running `helix-validate` on the NEW corpus against the OLD baseline produces
a mean Δ of **−19.7 percentage points**. This number is *misleading*:

- The OLD outputs that had DWARF (`hook_write`, `hook_read`,
  `fh_ftrace_thunk`) score higher because their identifiers and field names
  are real. The NEW outputs lose these to `vN`/`field_0xN`. **This is a
  pipeline difference (helix_tool vs extension), not an engine regression.**
- The functions where DWARF was *absent* in both runs (`hook_syslog`) score
  identically — confirming the engine output is unchanged.
- The genuinely new outputs (`fh_install_hook[s]`) score "0.0%" only because
  helix-validate's penalty-laden score happens to bottom out for code with
  many `vN` locals and trailing `unreachable_after_return` patterns. The
  raw fact is: where there was *no output at all* before, there are now 75
  and 95 lines of decompilation including resolved kernel-function calls.
  That is a step change, but helix-validate's *score* doesn't capture it
  cleanly because the score is built for comparing two well-formed outputs,
  not "nothing vs something."

This is an honest limitation of the methodology in its current form:
helix-validate measures *quality of emitted code*, not *amount of code
emitted*. A "silent failure resolved" event should count as a categorical
improvement (∅ → non-∅), but the current bounded scoring collapses it to
"0 vs something-also-low." Layer 3's classification (`new`/`removed`) is the
right signal for these cases; the rolled-up mean Δ should *exclude*
`new`/`removed` rows. Small fix, deliberately deferred — recording it here
as a known limitation rather than tuning the numbers around it.

## 7. Provisional verdict for v0.9.1 vs the paper

The v0.9.0 paper's contributions hold. This session adds:

- **PE/Win64 lift-path quality** (Echo Mirage entry_point, demonstrated in
  the earlier ROTTR investigations in this session).
- **A new lifter bug found** in hexcore-remill (declare + define collision).
- **Empirical confirmation** that the malware.ko ELF gaps the GAPS doc
  enumerates are *not* addressed by this session's fixes — they require
  separate work.

If a v0.9.1 supplement to the paper is to be written, this is the honest
shape: PE-side wins, ELF-side unchanged, methodology (`helix-validate`)
still useful but needs the `new`/`removed`-exclusion refinement before it
can carry a corpus-level claim of "engine got better." We have not earned
the headline number we'd want for a paper yet.
